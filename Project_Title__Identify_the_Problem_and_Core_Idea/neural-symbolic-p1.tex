\section{Project Direction and Updates}
Neurosymbolic AI is an emerging compositional paradigm that fuses neural learning with symbolic reasoning to enhance the transparency, interpretability, and trustworthiness of
AI. It also exhibits higher data efficiency making it promising for edge deployments \cite{cogsys}. Because the neural stage is compute bound, and the symbolic stage is memory bound, heteregenous hardware deployment, such as a specialized accelerator for each stage, is a natural fit. 
However, the interface between the two accelerators can become a bottleneck, limiting end-to-end performance. 

We therefore ask: \emph{after both ends of a neuro-symbolic pipeline are accelerated, does the interface between them become the bottleneck, and if so, which interface mechanisms remove it?} 

Visual Sudoku illustrates the problem. A neural network recognizes handwritten digits, and a SAT solver uses the recognized givens to complete the grid, following the task studied in SATNet~\cite{satnet}. The Sudoku rules are identical across puzzles; only the givens change. Yet SAT-Accel's host interface~\cite{sataccel} constructs and transfers a complete solver memory image for each instance. In our implementation, a puzzle with 36 recognized givens produces an image containing roughly 632\,KB of data. Much of this work reconstructs and moves information that the solver already received for the preceding puzzle.

Our eventual goal to solve this issue, if it exists, is to enable \emph{producer--consumer pipelining} between the neural and symbolic accelerators: predictions should flow into the solver's input path as they are produced, allowing inference, transfer, and solver-state preparation to overlap. ReasonLink will explore compact literal streams, on-chip buffering, and resident base constraints to support this execution model. This milestone builds the infrastructure and baselines needed to evaluate that design. We implemented serial and double-buffered software paths; double buffering overlaps conversion and transfer for puzzle $i{+}1$ with solving puzzle $i$. These baselines quantify the overhead the pipelined interface must reduce. Since then, SAT-Accel runs as RTL without Vitis, and a first ReasonLink stage passes end to end in RTL simulation.

\textbf{Changes since the proposal.} We moved from Chipyard/Gemmini to ESP~\cite{esp} with an Ariane core and NVDLA \emph{nv\_small} (int8). Immediate board access was unavailable, while the departmental server already provided the ESP toolchain and an existing NVDLA integration path. SAT-Accel~\cite{sataccel} remains the symbolic accelerator. Because the server has no \texttt{v++}/XRT, we compile its kernels with Vitis HLS alone and replace the Vitis linker and runtime with our own block design, shell, and driver. ReasonLink sits in the SAT-Accel tile and reads NVDLA's output from DRAM, since a combined tile was judged too costly. The workload, research question, and interface mechanisms are unchanged.

We also separated software exploration from hardware validation. The P1 timing pilot replays neural outputs from an int8 emulator and uses MiniSat~\cite{minisat} in place of SAT-Accel after decoding its memory image. SAT-Accel's unmodified kernels now run in functional and RTL simulation, but neural outputs are still replayed, and no result yet comes from the board. These results do \emph{not} establish system latency or speedup.

\section{Exploration and Findings}
\textbf{Locating the interface cost.} Inspection of SAT-Accel's host flow and our image-builder experiments showed that each puzzle rebuilds the same 729-variable, 11,988-clause base formula with a small set of new givens. For a representative puzzle with 36 givens, the replayed score array is 1,296 bytes, but the solver image occupies about 632\,KB of data within 10.5\,MB of allocated buffers. This suggests that compressing scores alone misses the main opportunity. We measured this directly: across 1,000 puzzles, a puzzle's image differs from the base formula's by only 1,212\,B of 632\,KB (0.19\%). SAT-Accel already applies unit clauses as level-0 fixed decisions. Passing the givens only that way, on one base image restored between puzzles, matches the unit-clause results on 1000/1000 puzzles. The kernels write back only per-run state, so the base image stays valid in DRAM. The interface can therefore keep the base formula resident and send only the givens.

\textbf{Software optimization and overlap.} We compared serial and double-buffered handoffs, each in two modes. \emph{Faithful} reproduces SAT-Accel's full-buffer clearing and copying; \emph{lean} clears and copies only used regions. Both use busy polling. Lean provides a stronger software baseline against which hardware changes must be justified. Double buffering uses two explicitly owned slots so conversion and copying for puzzle $i{+}1$ overlap solving puzzle $i$.

Table~\ref{tab:pilot} shows that used-region handling reduces serial wall time from 2.81 to 1.45\,ms per puzzle, before adding any ReasonLink hardware. Argmax takes less than 1\,$\mu$s; almost all conversion time is image construction. In serial runs, conversion, copying, and synchronization account for 73.6\% of their combined time with solving in faithful mode and 50.5\% in lean mode. These fractions exclude neural inference.

Double buffering barely improves faithful wall time but reduces lean wall time to 0.80\,ms per puzzle. The exposed fraction, defined as $(T_{\rm wall}-\sum T_{\rm solve})/T_{\rm wall}$, falls from 70.5\% to 5.1\% across those modes. Thus overlap depends on the relative stage costs, while lean still copies roughly 632\,KB per puzzle. These observations motivated testing base-formula reuse \emph{in software first} (the 1000/1000 check above), then measuring the additional benefit of a hardware literal producer. They are pilot evidence for the proposal's handoff and overlap hypotheses, not confirmation on ESP.

\textbf{ReasonLink, phase B, in RTL.} Our first ReasonLink core sits in front of the unmodified SAT-Accel. For each given cell, the CPU pushes the cell index and the address of NVDLA's output buffer. The core fetches the 10 int8 logits, takes the argmax over digits 1--9, and queues the literal in an on-chip FIFO, with a credit per cell because NVDLA reuses one output buffer. On commit, it writes the givens as a fixed-decision delta onto the resident base image. Table~\ref{tab:rtl} compares it with the host-built image flow in the same RTL build. Every run returns the reference result with identical search counts.

Conversion costs about 67 cycles per given, and the delta write takes 1,181 cycles. That is roughly 36\,$\mu$s per puzzle at 100\,MHz, compared with 0.7\,ms of lean CPU image construction on x86. Solve time is unchanged, however. SAT-Accel still copies the whole image in from DRAM on every solve, about 81k read beats ($\approx$650\,KB). Its memory master waits on memory in 92\% of busy cycles, and the search itself is short. Phase B thus removes conversion and transfer from the CPU, while the remaining interface cost moves into SAT-Accel's copy-in. Phase A targets that cost by keeping the base formula resident \emph{on chip}. These cycle counts depend on the testbench memory model, so only the board can measure real DRAM and NoC behavior.

\textbf{Workload limits.} The retrained classifier achieves 99.26\% given-cell accuracy, but only 79.0\% of puzzles recover the ground-truth grid; 19.2\% become UNSAT and 1.8\% are SAT with a wrong grid. Small perception errors compound across givens. We will therefore hold predictions fixed across interfaces and distinguish task accuracy from interface correctness. Separately, the current 24--40-clue puzzles require only 1.17 mean MiniSat decisions. They exercise loading more than search, so a harder workload is needed to test whether ReasonLink's benefit shrinks with longer solves.

\section{Implementation and Infrastructure Progress}
\textbf{Working software and tools.} We implemented the Sudoku encoder, 1,000 unique-solution puzzles with MNIST test images, classifier training and int8 emulation, and a PySAT~\cite{pysat} reference path. ESP's demo weights achieved only 74.5\% MNIST accuracy under the evaluated preprocessing; investigation found a mismatch between training preprocessing and the deployed int8 input path. Retraining the same architecture raised emulated int8 accuracy to 99.20\%. The emulator matches ESP's published reference output; the retrained model's hardware output remains unverified.

The C image builder matches SAT-Accel's original host implementation byte for byte in the compared initialized regions on all 13 test cases. The image-decode--MiniSat path agrees with the reference SAT/UNSAT result on all 1,000 puzzles. It returns 992 identical grids and eight alternative grids verified to satisfy their instances. All four baseline configurations return identical results to each other.

\textbf{SAT-Accel without Vitis.} SAT-Accel's 16 unmodified kernel sources run as threads in a functional model. They pass all 16 of its benchmarks, with decision and conflict counts identical to a build against Vitis HLS 2023.2's headers, and match the reference on 1000/1000 Sudoku puzzles. We synthesized the 7 kernels with Vitis HLS, halving clause capacity to fit beside Ariane and NVDLA. A Vivado block design, an APB/AXI shell, and a C driver core replace \texttt{v++} and XRT. All 16 RTL tests pass (11 Sudoku and 5 benchmarks, SAT and UNSAT). The out-of-context netlist uses 112k LUTs and 434 URAMs (45\%) and meets timing at 10\,ns (WNS $+$2.0\,ns).

We packaged it as an ESP third-party tile with a Linux driver, a user library, and a bare-metal test. The 2$\times$3 VCU118 SoC (Ariane, NVDLA, SAT-Accel) and a Linux image with both accelerators build end to end. The board harness implements full, CPU-delta, and ReasonLink handoffs, serial and double-buffered, and passes on the host against a simulated device. It checks every NVDLA output against our emulator.

The baseline harness records conversion, copying, synchronization, and solving with cycle counters. Static RISC-V builds are available; a local QEMU check matched native results on 50 puzzles. ESP is pinned to release 2026.1.0, and the server has Vivado/ModelSim 2023.2 and RISC-V GCC 9.2. Recompiling ESP's demo reproduced its NVDLA loadable byte for byte, and our retrained classifier also compiles for \emph{nv\_small}.

\textbf{SoC integration and measurement scope.} In full-SoC simulation, Ariane boots the bare-metal test and ESP's plug-and-play discovers the SAT-Accel tile. The CPU reads the tile's ID through the NoC, enables coherent DMA, and loads the instance image. The VCU118 SoC also passes Vivado synthesis. RTL cycle counts use the testbench memory model. P1's copy timings are CPU memory copies, and its solve times come from MiniSat. Single-run x86 timings cannot predict ESP performance.

Code, raw results, and reproduction details are maintained at \url{https://github.com/AaronCherian404/ReasonLink} in \texttt{workload/}, \texttt{handoff/}, \texttt{baselines/}, \texttt{sataccel\_sim/}, \texttt{sataccel\_hw/}, \texttt{esp\_soc/}, \texttt{board/}, \texttt{results/}, and \texttt{PROGRESS.md}.

The final evaluation will include neural execution, DMA/NoC traffic, and interface stalls. Reproducible code and experiment scripts will accompany the final report on December 18.
